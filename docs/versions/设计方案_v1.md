# 旅游团身份证登记 App — 设计方案 v1

> 目标：安卓手机上离线完成「新建旅行团 → 批量选身份证照片 → 自动提取姓名/性别/身份证号/登记日期 → 人工兜底核对 → 导出 xlsx/txt → 分享微信」。
> 硬约束：客人的身份证信息一次都不出手机。

---

## 0. 一句话结论

**Android 原生（Kotlin + Jetpack Compose）+ 离线打包版 ML Kit 中文 OCR + 三通道扰动识别 + 身份证号 MOD 11-2 校验位 + 自写最小 xlsx 生成器 + FileProvider 分享**。
APK 里**不声明 INTERNET 权限**——不是"承诺不上传"，是系统层面根本连不上网。

预计 4–5 个工作日可以出能装机用的第一版。

---

## 1. 为什么是这套技术栈

### 1.1 为什么原生而不是 Flutter / 小程序

这活的三条命脉全在原生层：相机与相册选择器（Photo Picker）、离线 OCR 的 ML Kit 绑定、FileProvider 分享给微信。Flutter 要在每一条上再套一层插件，插件质量参差，出错时排查成本翻倍；而本 App 界面就四个页面、没有复杂动画，用不上跨平台的价值。包体也更小。

- `minSdk 26`（Android 8.0，覆盖 95% 以上在用机型）
- `targetSdk 35 / compileSdk 35`
- Kotlin 2.x、JDK 17、AGP 8.x、Gradle 8.x（Kotlin DSL，version catalog 管理依赖）
- 单模块起步（`app`），导出与 OCR 逻辑拆成 `:core-ocr`、`:core-export` 两个纯 Kotlin library，方便写单元测试（JVM 上直接跑，不用开模拟器）

### 1.2 为什么必须是"打包版"ML Kit

ML Kit 文字识别有两个发行通道，**必须选错不可的那一个**：

| 依赖 | 模型在哪 | 能不能离线首跑 | 要不要 Google 服务 |
|---|---|---|---|
| `com.google.mlkit:text-recognition-chinese:16.0.1` | 打进 APK（约 +15–20 MB） | 能 | **不需要** |
| `com.google.android.gms:play-services-mlkit-text-recognition-chinese:16.0.1` | 运行时从 Play 服务下载 | 不能 | 需要 GMS |

旅游社前台用的多半是国产机（华为、荣耀、小米、OPPO），很多**没有 GMS**。选第二个通道，App 会在这些机器上直接不可用，而且首次识别要联网下载模型——正好踩在"不上传客人信息"的红线上。所以锁死 `com.google.mlkit` 那个包。

### 1.3 OCR 引擎的备选

ML Kit 中文版对印刷体证件效果稳定，但它只吐「文字块 + 坐标」，结构化得自己写。若实测某些机型/某些卡面识别率不达标，v2 可加 PaddleOCR-Lite（ncnn 版，纯 C++ 推理）做第二引擎与第四路投票。**v1 不做**，理由是集成要 NDK、包体 +80 MB、调试周期长，而下面的"校验位 + 三通道"组合已经能兜住绝大多数错。

## 2. 核心难点：三次识别怎么才有意义

这是整个方案里唯一需要设计而不是堆代码的地方。

**同引擎、同一张图、连跑三次，结果 100% 一模一样。** 直接"跑三次比对"等于没比对——它只会给你三次相同的自信，包括三次相同的错误。要让三次独立，必须让**三次的输入不一样**，模拟三个不同的"读图条件"：

| 通道 | 预处理 | 模拟的场景 |
|---|---|---|
| A | 原图，但先做 ROI 粗定位（找卡面最大矩形 → 透视校正 → 裁出号码行带）再识别，放大到长边 ≥1600 px | 正常拍摄，追求最好那一次 |
| B | 转灰度 → CLAHE 局部对比增强 → 自适应阈值二值化 | 塑料卡反光、磨砂贴膜、背景花纹干扰 |
| C | 旋转 +1.2°（模拟手歪）→ 2× 上采样 → 轻锐化 | 手持略歪、对焦偏软 |

三份输出各自归一化后再比对（归一化顺序很关键）：

1. 全角转半角、统一去空格与不可见字符
2. 按"号码段/姓名段/日期段"分区，分区内做易混字符映射：`O o Q D → 0`、`I l | → 1`、`Z → 2`、`S → 5`、`B → 8`、`G → 6`（**只在纯数字段内**做，姓名段不能碰，否则"吕"会被改坏）
3. 比对三份结果，逐字段给出一致/不一致

**三个字段的判定规则不同**，这是提高自动通过率的关键：

- **身份证号**：三份一致 **且** 通过 ISO 7064 MOD 11-2 校验位 → 自动通过。校验位不通过一律进人工，不管几次一致——校验位能抓掉 90% 以上的单字符错误，比"三次一致"更硬（三次错成同一个号在理论上可能，比如反光正好盖掉一位且三次都补成同一个数字）。
- **性别**：**根本不做 OCR**。从号码第 17 位推（奇=男、偶=女）。零成本、零错误率，还省掉一路人工核对。
- **出生日期**：从号码第 7–14 位推，再用 OCR 出的"出生"栏交叉验证；不一致只提示、不改号。
- **姓名**：三份一致 **且** 2–4 个汉字 **且** 落在「姓名」二字锚点的右/下邻接区域 **且** 全字在 GB2312 常用字表内 → 自动通过。生僻字（异体字、少数民族姓名用字）一律进人工，因为这类错最难自己发现。

> 用户提的"三次不同就人工"逻辑照办，但**加了一条**：身份证号校验位不过也必须人工。这条不加，会出现「三次一致但号码是错的」漏网，而号码错正是后果最重的那种错（保险买不上、进不了景区）。

## 3. 数据模型

```
Team        团
  id, name, teamCode(团号), departDate, note, createdAt

Member      成员
  id, teamId, seq
  name, gender(M/F), idNumber, birthDate
  registerDate          // 登记日期，默认=录入当天，可手改
  status                // AUTO_OK | NEED_REVIEW | MANUAL_OK | OCR_FAILED
  rawCandidates         // JSON：三通道各自的原始识别文本与归一化结果（供核对页展示，可关）
  reviewTarget          // 三份结果里分歧的字段位图，供核对页默认聚焦
  note
  createdAt, updatedAt
```

约束：同一团内 `idNumber` 唯一（导入时命中重复 → 黄条警告"该号码已在团内第 3 位"，不硬拦，因为确实可能同名同证件重复登记需人工判断）。

**原图策略（v1 默认）**：识别完成后立即删除工作副本；只有进入 `NEED_REVIEW` 的那几张，保留**裁出的号码区+姓名区小图**（约 100 KB）直到用户确认后删除。用户可以在设置里选"全部不保留"或"全部保留到导出后删除"。

## 4. 界面：四个页面 + 一个确认页

给 Claude 的设计任务按这个结构出稿。定位不是"潮玩 App"，是**旅行社前台在强光下、单手、一次处理三十个人**的工具。

1. **团列表**：卡片流。每卡：团名、人数、待核对红点、出发日期。右下 FAB「新建团」。
2. **录入页**：顶部大按钮「批量选择照片」（Photo Picker 多选，单次上限 100 张）；下方是处理队列，一人一行：缩略图 + 姓名/号码（识别出来就显示，没有就显示"—"）+ 状态徽标。底部常驻「继续添加」「去核对(n)」「导出」。
3. **核对页**（最关键的一屏）：上下分栏——上半是号码区放大图（支持双指缩放、可左右滑看上/下一张），下半是三个字段的三份候选对照，点候选即填充，或直接调键盘改；分歧字段高亮成琥珀色并自动聚焦。"确认并下一条"按钮常驻底部，滑动手势也绑定同一动作。
4. **成员表**：可排序的列表（序号/姓名/性别/号码/登记日期/状态），支持行内编辑、长按删除、下拉搜索。
5. **导出确认页**：导出前必须过这一屏——表格预览（前 5 行 + 总行数）、勾选要导出的列、选 xlsx 还是 txt、填文件名（默认 `{团名}_{YYYYMMDD}`）、开关「导出后清空本团数据」。点「确认导出」→ 生成 → 唤起分享。

**设计约束（写进给 Claude 的 brief）**：

- 正文字号 ≥ 16sp，按钮高 ≥ 48dp，单手可达区（拇指弧）内放主操作
- 高对比度、低色阶：背景暖白 `#FDFBF7`，主色深靛蓝 `#1F5AA6`，状态色只有三档（灰=待处理、绿=已通过、琥珀=需人工）。不用渐变、不用玻璃拟态、不用大面积插画
- 表格类信息用等宽数字（`FontFeatureSettings("tnum")`），身份证号分组显示 `110101 19900101 1234`
- 暗色模式 v1 不做（户外强光下没人用暗色）

> 注：这跟你平时偏好的奶油低饱和插画风是两套语言。工具类 App 我建议走"干净、克制、专业"，别把治愈系带进来。这一条要你点头。

## 5. 导出

### 5.1 xlsx：自己写，不引 Apache POI

POI 在 Android 上是灾难：dex 方法数爆表、要开 desugar、包体 +12 MB，而我们要的只是"一个 sheet、七列文本"。直接 `java.util.zip.ZipOutputStream` 拼 OOXML：

```
[Content_Types].xml
_rels/.rels
xl/workbook.xml
xl/_rels/workbook.xml.rels
xl/worksheets/sheet1.xml
xl/styles.xml
```

单元格全走 `t="inlineStr"`，不建 sharedStrings，省一层索引。整个生成器约 250 行 Kotlin，零依赖，JVM 上可直接单测（断言解压后 XML 结构 + 用 Python `openpyxl` 读回来核验）。

**必踩的坑**：身份证号是 18 位纯数字，Excel 会当数值处理成 `1.10101E+17`。必须给该列设文本格式（`numFmtId=49` 的 `@` 格式，或整格写 `inlineStr`）。导出后一定要 `openpyxl` 读回来断言 `type(cell.value) is str` 且长度 18——这是验收项，不是"注意一下"。

列：`序号 | 姓名 | 性别 | 身份证号 | 出生日期 | 登记日期 | 备注`。

### 5.2 txt：UTF-8 带 BOM

`\uFEFF` + Tab 分隔 + CRLF 行尾。不带 BOM 的话，微信里用手机自带记事本或老版 WPS 打开会乱码——这是国内分享场景的固定坑，必须加。

### 5.3 分享微信

```kotlin
val uri = FileProvider.getUriForFile(ctx, "$packageName.fileprovider", file)
val intent = Intent(Intent.ACTION_SEND).apply {
    type = if (xlsx) "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"
           else "text/plain"
    putExtra(Intent.EXTRA_STREAM, uri)
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
ctx.startActivity(Intent.createChooser(intent, "分享到"))
```

微信能直接收 xlsx 并内置预览，也能发到"文件传输助手"。**别用 `type="*/*"`**，部分微信版本会拒绝。文件写到 `cacheDir/export/`，`filepaths.xml` 只暴露这一个子目录。

关键点：分享是**把 URI 交给微信 App**，本 App 全程不需要网络——所以"零 INTERNET 权限"和"能发微信"不冲突。

## 6. 信息安全：靠权限表，不靠承诺

1. **`AndroidManifest.xml` 不声明 `android.permission.INTERNET`**。这是整套方案里最硬的一条：进程根本无法创建 socket。用户在「设置 → 应用 → 权限」里看到网络权限是"无"，这是可以当场给客户验的。
2. **不申请任何存储权限**：新版走 `PickMultipleVisualMedia`（Photo Picker），Android 11 以下走 SAF `ACTION_OPEN_DOCUMENT`。拿到的是一次性授权 URI，不遍历相册。
3. **ML Kit 打包版**：模型在 APK 内，运行时不下载模型、不联网校验。
4. **数据只落应用私有目录**：`Room` 数据库 + 应用沙盒，其他 App 读不到（Android 10+ 分区存储）。
5. **默认不留原图**，只有待核对项留小裁片，确认后即删。
6. **一键清空本团** + 「导出成功后自动清理」开关。
7. 崩溃日志不接任何上报（不引 Firebase/Crashlytics）。
8. v2 可选：SQLCipher 加密数据库（包体 +5 MB）。v1 先不做——因为无网络权限的前提下，攻击面只剩"手机被人拿走"，那属于锁屏与文件加密（系统级）该管的事。

**落地时必须核对**：`./gradlew :app:dependencies` 里所有传递依赖不得引入带网络能力的 SDK；最终 `aapt dump permissions app-release.apk` 输出里不能出现 INTERNET。写进验收清单。

## 9. 验收清单（硬指标，逐条验）

1. 拿 20 张真身份证（脱敏/本人同意）做测试集，**自动通过率 ≥ 85%**、**误通过率（自动通过但号码错的）＝ 0**。误通过是红线，宁可全进人工。
2. `aapt dump permissions` 无 `INTERNET`；飞行模式下全流程（选图→识别→核对→导出→分享）能走完。
3. 导出的 xlsx 用 `openpyxl` 回读：身份证号是 `str` 且 18 位；txt 用微信打开不乱码。
4. 华为/无 GMS 机型（或模拟器无 Google Play 镜像）上 OCR 正常运行。
5. 一次选 50 张图不 OOM（内存峰值 < 300 MB，逐张释放 Bitmap）。
6. 断网、灭屏、切后台再回来，队列不丢。
7. 导出后"清空本团"确实清掉数据库行与 cacheDir 里残留文件。

## 10. 风险与已知边界

- **反光/贴膜/斜拍的号码行**：三通道 + 校验位能兜大半，但必然有一部分要人工。真实预期自动通过率 80–90%，别按 100% 设计流程。
- **一图多证**（把一家人拍在一张图上）：v1 **不做切分**，假设一图一证；遇到会识别出多组号码，直接标记 FAILED 让人工录。v2 再考虑多实例切分。
- **生僻字姓名**：少数民族与异体字一律进人工，不强求。
- **微信分发 APK**：微信对直接传 apk 有限制（会被拦或提示风险）。实际分发走企业微信、QQ、或直接拷到手机安装，需用户手动允许"未知来源"。不上架应用商店。
- **Android 15+ 的 Photo Picker 行为差异**：targetSdk 35 要在 Android 15 真机/模拟器上过一遍。
- **保单号/房型/护照号**：v1 不做，数据模型留扩展位，v2 按需加列。

## 11. 要你拍板的四件事

1. **登记日期**：默认"处理当天，可手改"，对不对？还是应该默认成团的出发日期？
2. **原图保留**：默认只在待核对时留号码区小图、确认后删。要不要给"全部保留"选项？
3. **是否需要额外列**：保险单号、房型、护照/港澳台通行证号——v1 不做，但你现在说了我就留好格子。
4. **给谁用**：只你自己这台手机，还是要给同事也装？（影响签名策略与更新方式：给自己 = 一个固定 keystore 手动发 APK；给多人 = 得考虑版本号与"覆盖安装不能丢数据"的迁移测试）
