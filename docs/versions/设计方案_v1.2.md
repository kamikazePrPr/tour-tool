# 旅游团身份证登记 App — 设计方案 v1.2

> 目标：安卓手机上离线完成「新建旅行团 → 批量选身份证照片 → 自动提取姓名/性别/身份证号 → 人工兜底核对 → 打标签备注 → 导出 xlsx/txt → 分享微信」。
> 硬约束：客人的身份证信息一次都不出手机；相册里的原图一张都不动。
> v1.2 变更：人工核对一律看**相册原图本身**（不再用号码区裁片）；删去多人分发/签名/迁移那一整节与 PIN 锁提议；标签改为随手可加，不再征询预设清单。

---

## 0. 一句话结论

**Android 原生（Kotlin + Compose）+ 打包版 ML Kit 中文 OCR + 三通道扰动识别 + 身份证号 MOD 11-2 校验位 + 自写最小 xlsx 生成器 + FileProvider 分享**。APK 不声明 INTERNET 权限——不是承诺不上传，是进程连 socket 都建不出来。工期 4–5 个工作日到能装机版。

## 1. 技术栈

原生而不是 Flutter/小程序：这活的命脉全在原生层（相册选择器、离线 OCR 绑定、FileProvider 分享），套一层跨平台只会增加排查成本，而界面就四页、没有复杂动效。

- `minSdk 24`、`targetSdk 35`、Kotlin 2.x、JDK 17、AGP 8.x、Gradle 8.x
- `:app`（UI）+ `:core-ocr`（识别与解析）+ `:core-export`（表格生成），后两个是纯 Kotlin 库，单测在 JVM 上跑，不开模拟器

### 1.1 OCR 引擎：必须是打包版

| 依赖 | 模型位置 | 离线首跑 | 需要 GMS |
|---|---|---|---|
| `com.google.mlkit:text-recognition-chinese:16.0.1` | APK 内（+15–20 MB） | ✅ | ❌ 不需要 |
| `com.google.android.gms:play-services-mlkit-text-recognition-chinese` | 运行时从 Play 服务下载 | ❌ | ✅ 需要 |

选第二条线不光可能在没 GMS 的机器上直接不可用，首次识别还要联网下模型，正好踩红线。锁死第一条。

## 2. 三次识别怎么才有意义（核心技术点）

同一张图、同一个引擎连跑三次，结果一模一样，包括错的地方。所以三次必须是**三种不同的输入条件**：

| 通道 | 预处理 | 模拟场景 |
|---|---|---|
| A | 原图 → 卡面定位/透视校正 → 裁出号码行带 → 放大到长边 ≥1600 px | 正常拍摄，求最好那次 |
| B | 灰度 → CLAHE 局部对比增强 → 自适应阈值二值化 | 塑料卡反光、磨砂贴膜、花纹背景 |
| C | 旋转 +1.2° → 2× 上采样 → 轻锐化 | 手略歪、对焦偏软 |

三份结果按"号码段 / 姓名段 / 日期段"分区后各自归一化（全角转半角、去空格、数字段内做 `O Q D→0`、`I l |→1`、`Z→2`、`S→5`、`B→8`、`G→6`；**姓名段绝不做这个映射**，否则「吕」会被改坏），再逐字段比对。

判定规则：

- **身份证号**：三份一致 **且** 通过 ISO 7064 MOD 11-2 校验位 → 自动通过。**校验位不过一律人工**，不管三次多一致——反光盖掉一位、三次补成同一个数字这种情况，只有校验位抓得住。
- **性别**：**不 OCR**。从号码第 17 位奇偶推（奇男偶女），零成本零错误。
- **出生日期**：从号码 7–14 位推，OCR 出的"出生"栏只做交叉提示，不改号。
- **姓名**：三份一致 + 2–4 个汉字 + 落在「姓名」二字锚点右/下邻接区 + 全字在 GB2312 常用字表内 → 自动通过；生僻字/少数民族用字一律人工。

这些预处理图全部是**内存里的 Bitmap** 加上 `cacheDir` 下的临时文件，用完即删（见第 4 节）。

## 3. 数据模型

```
Team    团
  id, name, teamCode, departDate, note, createdAt

Member  成员
  id, teamId, seq
  name, gender, idNumber, birthDate
  registeredAt          // 登记时间：处理当时（精确到分钟），仅 App 内显示，不导出
  status                // AUTO_OK | NEED_REVIEW | MANUAL_OK | OCR_FAILED
  sourceUri             // 相册原图的 content:// URI（核对时直接读它，不复制）
  uriPermissionHeld     // 是否成功持久化了该 URI 的读权限
  note
  createdAt, updatedAt

Tag     标签（全局库）
  id, label, colorIndex, sortOrder
MemberTag  多对多：memberId, tagId
```

**导出列**：`序号 | 姓名 | 性别 | 身份证号 | 出生日期 | 备注 | 标签`。登记时间不导出。标签列默认带上，导出确认页可勾掉。

**约束**：同团内身份证号重复 → 黄条警告"该号码已在团内第 3 位"，不硬拦。

## 4. 原图与临时文件：一寸都不碰用户的相册

1. **相册原图只读、只引用**。通过 Photo Picker / SAF 拿到只读 URI，App 全程只读，不删、不挪、不改名、不复制一整份到应用目录。识别完那张照片跟没被碰过一样。
2. **核对页显示的就是相册原图本身**（第 5 节），只看不拷。
3. **中间产物全部在 `cacheDir/work/<uuid>/`**：透视校正图、二值化图、旋转图、号码行带。都是应用私有沙盒——不出现在相册、文件管理器默认看不到、系统空间紧张时自动回收。
4. **即用即删**：每张图识别完（成功或失败）立刻删该目录下全部文件，异常路径走 `finally`。处理五十张之后 `cacheDir/work` 应为 0 字节。
5. **绝不调用 MediaScanner / 写 MediaStore**，绝不往 `Pictures/`、`DCIM/`、`Download/` 写任何东西。

> 一句话：用户手机里能看见的东西，一张不多也一张不少；相册里那张照片，字节级不变。

---

## 5. 核对页怎么显示原图（这是 v1.2 的重点）

核对页上半屏显示**相册原图全图**，不是裁片。三个技术点：

**① 让 URI 活过重启。** Photo Picker 返回的 URI 默认只在本次会话有效。选图后立刻对每个 URI 调：

```kotlin
contentResolver.takePersistableUriPermission(
    uri, Intent.FLAG_GRANT_READ_URI_PERMISSION
)
```

成功就把 `uriPermissionHeld = true` 写进数据库，重启 App、隔天再打开团，核对页照样能读原图。清空本团时统一 `releasePersistableUriPermission`，不留一堆授权。

**② 不落副本，按屏解码。** 身份证照片多是一千二百万到四千万像素，直接解成 Bitmap 必 OOM。用两段式：`inJustDecodeBounds` 取原始尺寸 → 按屏宽算 `inSampleSize` → 只解一张屏幕级的；滑到下一个人时先回收上一张。全流程内存峰值控制在 300 MB 以内。

**③ 放大看号码要清晰。** 屏幕级 Bitmap 放到 3 倍就糊了，看不清那一位到底是 3 还是 8。所以缩放超过 2 倍时切到 `BitmapRegionDecoder`，按当前视口只解目标区域的原生像素（一次约 1024×1024），拖动时滚窗重解。四千万像素的原图放大到每一位数字都锐。

**④ 兜底。** 个别系统（老 ROM、部分企业定制机）会拒掉持久授权，或者用户在核对前把相册里那张删了。两种情况都降级：前者在应用私有目录放一张长边 1600 的 JPEG（约 200–400 KB，同样不可见，确认后删）；后者在核对页显示「原图已不在相册，请重新拍一张或手动录入」，并把该条标为 OCR_FAILED。

## 6. 界面（给 Claude 的 brief）

四页 + 一个导出确认页。定位不是潮玩 App，是旅行社前台在强光下、单手、一次处理三十个人的工具。

1. **团列表**：卡片流。团名、人数、待核对红点、出发日期。右下 FAB 新建团，左右滑动删除（二次确认）。
2. **录入页**：顶部「批量选择照片」（多选上限 100 张），下方处理队列逐条显示缩略图、已识别出的姓名/号码、状态徽标。底部常驻「继续添加 / 去核对(n) / 导出」。
3. **核对页**：上半是**相册原图全图**（双指缩放、拖动，放大自动切高清区、左右滑切人），下半是三份候选对照，点候选即填、也可直接改键盘。分歧字段琥珀色高亮并自动聚焦。底部常驻「确认并下一条」。
4. **成员表**：序号/姓名/性别/号码/状态，顶部按标签筛选（多选），行内编辑，长按删除，搜索。
5. **导出确认页**：表格预览（前 5 行 + 总行数）、列勾选、xlsx/txt、文件名（默认 `{团名}_{YYYYMMDD}`）、「导出后清空本团」开关，点确认才生成。

**设计约束**：正文 ≥16sp、按钮 ≥48dp、主操作放拇指弧内；背景暖白 `#FDFBF7`、主色深靛蓝 `#1F5AA6`、状态色只有灰/绿/琥珀三档；不用渐变、不用玻璃拟态、不用大面积插画；号码用等宽数字（tnum）分组显示 `110101 19900101 1234`。暗色模式 v1 不做。

> 这套是"干净克制"的专业工具语言，跟你平时偏好的奶油低饱和治愈系是两套东西，工具类 App 我建议不带治愈风。

## 7. 标签与备注

标签是**全局库**：这一团建的「孕妇」，下一团直接能用。输入框里随手打一个新词回车即建，颜色自动分配，可改可删。成员可挂多个标签，成员表顶部按标签多选筛选，导出时标签列默认带上、可勾掉。备注是每人一个自由文本框。

预置几个高频例子（孕妇、高龄、儿童、免票、半票、退伍军人），首次启动写入，用户随便删改。全部开放给现场自己定义，不需要事先定死清单。

## 8. 导出

### 8.1 xlsx：自己写，不引 POI

POI 在安卓上要开 desugar、方法数爆表、包体 +12 MB，而我们要的只是一个 sheet 七列文本。直接 `ZipOutputStream` 拼 OOXML（`[Content_Types].xml`、`_rels/.rels`、`xl/workbook.xml`、`xl/worksheets/sheet1.xml`、`xl/styles.xml`），单元格全走 `inlineStr`，约 250 行 Kotlin，零依赖，可在 JVM 上单测。

**必踩的坑**：18 位身份证号会被 Excel 当数值显示成 `1.10101E+17`。必须给该列设文本格式（numFmt `@`）。导出后我会用 `openpyxl` 读回来断言 `type(cell.value) is str` 且长度 18，这是验收项。

### 8.2 txt：UTF-8 带 BOM

`\uFEFF` 开头 + Tab 分隔 + CRLF。不带 BOM 的话微信里用手机记事本打开就是乱码。

### 8.3 分享微信

```kotlin
val uri = FileProvider.getUriForFile(ctx, "$packageName.fileprovider", file)
Intent(Intent.ACTION_SEND).apply {
    type = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet" // txt 用 text/plain
    putExtra(Intent.EXTRA_STREAM, uri)
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}
```

微信能直接收 xlsx 并内置预览，也能发文件传输助手。别用 `type="*/*"`（部分版本会拒）。分享是把 URI 交给微信 App，联网的是微信——所以"零 INTERNET 权限"和"能发微信"不冲突。

## 9. 安全

1. **不声明 INTERNET 权限**。进程建不了 socket，用户在设置里看到网络权限是"无"，可以当场给客户验。
2. **不申请存储权限**：新版走 Photo Picker，Android 11 以下走 SAF，拿到的是一次性只读 URI。
3. **ML Kit 打包版**：模型在 APK 内，运行时不下载、不联网校验。
4. **数据只落应用私有目录**，其他 App 读不到（分区存储）。
5. **相册原图不动**，中间产物即用即删（第 4 节）。
6. **一键清空本团** + 「导出成功后自动清理」开关；清团时释放全部 URI 授权。
7. 不接任何崩溃上报（无 Firebase/Crashlytics）。

**验收**：`aapt dump permissions app-release.apk` 里不能出现 INTERNET；飞行模式下全流程走完。

## 12. 验收清单

1. 20 张真证测试集：**自动通过率 ≥85%**，**误通过率（自动通过但号码错）= 0**。误通过是红线，宁可全进人工。
2. `aapt dump permissions` 无 INTERNET；飞行模式全流程能走完。
3. 处理完 50 张后 `cacheDir/work` 为空；**相册原图字节级未变**（比对 size + mtime），且相册里没有新增任何文件。
4. 核对页能显示原图并放大到看清单个数字；重启 App 后仍能显示。
5. 导出的 xlsx 用 openpyxl 回读：号码是 `str` 且 18 位；txt 微信打开不乱码。
6. 无 GMS 机型（或 AOSP 模拟器）OCR 正常。
7. 一次 50 张不 OOM（峰值 <300 MB）。
8. 灭屏、切后台、断网回来队列不丢。

## 13. 风险与边界

- 反光/贴膜/斜拍的号码行：三通道 + 校验位兜大半，真实自动通过率 80–90%，别按 100% 设计流程。
- 一图多证：v1 不做切分，识别出多组号码直接标 FAILED 让人工录。
- 生僻字姓名：一律人工。
- 原图被用户提前从相册删除：核对页显示提示并要求重拍或手录。
- 极端情况下的持久 URI 授权失败：降级为私有目录压缩副本（200–400 KB，确认后删）。
